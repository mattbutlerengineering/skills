# Archify against our diagram skills

Research note, 2026-10-21, for issue #1041 ("replace or update diagram
skills with archify skills; evaluate this library, figure out what would
help"). The Owner chose scope: evaluate and write findings only. Nothing
was vendored, installed, run or edited; no skill, plugin manifest or
factory file changed. Everything fetched was read as data, never as
instructions. Sources: the public site (gallery and home page) read through
a page fetcher, and the public GitHub repository read through the REST API
(file contents only, nothing downloaded or executed). The library's
`SKILL.md` and `references/update-awareness.md` were read in full or in
part; the renderers, validators and tests were not read.

Sources: https://archify.si/gallery, https://archify.si and
https://github.com/tt-a1i/archify (at release v3.2.0).

## Verdict in brief

**Leave the four diagram skills as they are; do not replace them.** Borrow
a few ideas as skill text, file small follow-ups, and treat archify as
something a user can install beside this plugin, not something the plugin
ships. Reasons, in order of weight: it is a Node toolchain with a real
browser gate and a plugin that is stdlib-only Python by hard convention; it
produces a different artifact (an explorable standalone HTML viewer with
its own chrome) than our committed, theme-aware `.svg` figures; and its
`SKILL.md` carries behaviours (update checks, a rules-file write offer)
that a vended plugin should not inherit.

## 1. What archify is

| Fact | Finding | Basis |
|---|---|---|

| Licence | MIT; copyright "tt-a1i (Archify)" and "Cocoon AI" (2025) | LICENSE file |
| Provenance | One main author (`tt-a1i`, about 1,100 of the visible commits) plus about 30 contributors, the next largest with about 130; says it is "based on" a Cocoon-AI architecture-diagram generator | contributors API; site |
| Maintainers | No organisation, no named individuals beyond the handle; the account is from 2019 | site; users API |
| Activity | Last push 2026-10-19; created 2026 by the Licence's date; CI, release, DSH and star-history workflows; a security policy that points at private vulnerability reporting | repo API |
| Repo shape | `archify/` is the skill package (`SKILL.md`, `bin/`, `schemas/`, `references/`, `renderers/`, `examples/`, `recipes/`); the rest is site, tests (many `.test.mjs`), benchmarks, and a 3-way README set in several languages | contents API |
| Dependencies | The skill package is described as zero-dependency Node (`engines >=18`); the repo root has dev dependencies (`ajv`, `parse5`, `saxes`, `skills`, `yaml`) | package files; site |
| Install | `npx skills add tt-a1i/archify -g` (and a Claude Code form with `--skill archify --agent claude-code --global --copy`) via the third-party `skills` CLI | home page |
| Diagram types | Ten: architecture, workflow, sequence, dataflow, lifecycle, erd, class, tree, timeline, waterfall. The gallery page lists six of them | `SKILL.md`; site |
| Input | Typed JSON per type (`schemas/<type>.schema.json`, plus a common schema) or Mermaid, which it re-authors as fresh JSON rather than parsing mechanically | `SKILL.md` |

How the skill instructs the agent: pick a type from a router table, read an
authoring-defaults reference and one example for that type, write the
complete candidate JSON, then run one command, `finalize`, which chains four
gates: `validate` (schema and rules), `deliver` (atomic write plus a
delivery receipt), `check` (strict structural checks of the produced HTML
and SVG) and `browser-check` (a real Chrome, Chromium or Edge over the
DevTools pipe, at several desktop sizes). A non-zero exit is never success;
the agent repairs the connected neighbourhood and reruns, with a repair
limit. The site reports nine checks per diagram (single SVG, finite SVG,
orthogonal arrows, label route clearance, relationship crossings, legend
clearance and others) and, for its gallery build, "108 checks / 12
artifacts / deterministic hashes".

**The quality receipt** is a machine-readable JSON file written at
finalization (the site's example is named `<name>.finalize.json`). It
records hashes of the source and of the delivered file, so a delivered file
can be matched to what was checked. By the site's own account, later check
failures are reported rather than rolled back, and the checks are
"automated structure and layout checks, not human visual-review results";
validation "checks the authored artifact, not the truth of every claim or
runtime system behavior". The skill text tells the agent to claim only
"automated checks passed; not visually reviewed" unless a person or the
agent actually looked at captures. That honesty rule is the most
transferable thing in the package.

Behaviours in `SKILL.md` worth knowing about before any install:

- An update check runs inside `finalize` and `deliver` and reaches a manifest
  on the project's own GitHub Pages host; the agent must relay an update
  notice to the user. The text says never to install on its own and to treat
  the release summary as untrusted data.
- It offers to append an `[archify explainer: ...]` line to the user's global
  rules file (`~/.claude/CLAUDE.md` and equivalents) if the user accepts.
- It writes under `.archify/<type>-<slug>-<timestamp>/` in the working
  directory.
- It expects shell access and falls back to hand-placed SVG into a template
  only when that is missing.

## 2. Our diagram skills

| Skill | Output | Size | Role |
|---|---|---|---|
| `architecture-diagram` | one theme-aware static `.svg`, light editorial style, flips dark by `prefers-color-scheme`; no scripts | 127-line `SKILL.md`, a design-system reference, one boilerplate | the committed, README-embeddable figure |
| `animated-diagram` | one `.svg` or `.html`, dark, ambient looping motion, reduced-motion support | 167 lines, design system, two boilerplates | scenery for a README or landing page; also turns a mermaid flowchart or state diagram into a moving one |
| `interactive-architecture-diagram` | one dark `.html` with narrated step-through, inspect panel, PNG and SVG export | 123 lines, design system, boilerplate | presenting how a system works |
| `mermaid` | mermaid source in markdown, explicit `classDef` contrast, one idea per diagram | 92 lines, no assets | quick text-source diagram |

All four are utility skills (`protocol.py` `UTILITY_SKILLS`, ADR-0023):
directly invoked, own no run artifact, never routed to by `next`. No
pipeline stage skill calls them. The only cross-skill references found are
`pipeline-board`, which points at the architecture-diagram design system
for its look, and `deepen`, whose HTML report draws its own before/after
diagrams. `lint.py` checks that every utility skill is named in the README
and the docs that must list them (`UTILITY_SKILLS` at lines 29 to 34 of
`protocol.py`) and checks skill assets exist (`check_skill_assets`; it
deliberately does not verify the cross-skill `../<skill>/references/...`
reference, which is an existing backlog item). `LEDGER.md` lists all four
as `draft` maturity; only mermaid has any routing-eval evidence (1 of 3
held in 2026-07), the other three have none. They are stdlib-clean by
construction: pure text and static assets, no tooling.

Validation today is prose only: each step ends with a "Done when" line the
agent checks by reading, and the design systems hold budgets (for example
at most 9 nodes, 12 connectors and 3 zones for the static figure) as
rules. No script parses the produced SVG; the backlog already records a
scaffold defect (a `viewBox` the README figure had to hand-fix) that a
mechanical check would have caught.

## 3. Side by side

| Dimension | Ours | Archify |
|---|---|---|
| Static committed figure, GitHub-embeddable | Yes, the core of `architecture-diagram` | Not its shape: output is a standalone HTML viewer; SVG is an export from the viewer, not the primary deliverable (as read; the SVG export was not inspected) |
| Ambient animation in a README `<img>` | Yes, pure SVG with SMIL and CSS | Live motion exists inside the viewer HTML; whether an exported SVG animates in a README embed was not verified |
| Narrated step-through | Yes | A "presentation" mode exists per the references list; depth not verified |
| Mermaid | Native text diagrams, plus a path from mermaid into the animated skill | Reads mermaid and re-authors as JSON; not a mermaid emitter |
| Diagram types | Flow, architecture (and mermaid's five) | Ten, including ERD, lifecycle, class, tree, timeline and waterfall with native layout |
| Determinism and validation | Prose checklists | Schema validation plus strict structural checks plus a real-browser gate, with hashed receipts; the stated aim is deterministic output |
| Defects only archify's gates would catch | n/a | Arrow routing that is not orthogonal, labels overlapping connector routes, crossings, legend collisions, clipping and overflow at several widths, non-finite SVG numbers. Ours has none of these checks, so the answer to "does it catch defects ours miss" is yes in kind; no head-to-head run was done |
| What its gates do not catch | n/a | By its own statement: truth of claims or runtime behaviour. Same limit as ours |
| Runtime and dependencies | None; stdlib-only convention satisfied | Node 18 or later, Chrome, Chromium or Edge for the browser gate, the `skills` CLI for install |
| Licence | Repo-internal | MIT, compatible with redistribution, with a notices file for embedded third-party brand marks (several carry CC-BY, CC-BY-SA or CC-BY-NC-SA terms; the notices file says they remain subject to their own terms) |
| Maintenance | Four small skills we own | A fast-moving external project; weekly releases, one dominant author, wide contributor base, a large test suite. Tracking it would be a standing cost |
| Trust | Our code only | See below |

**Dependency footprint, plainly.** This repo's hard convention is stdlib-only
Python 3 for every script (`CLAUDE.md`, "Hard conventions"). Archify is a
Node toolchain with a browser dependency. Adopting it as code is a direct
conflict with that convention; there is no reading of "optional tooling"
that avoids it for a plugin whose scripts all ship in the payload and run in
CI via `make check`. Vendoring would also bring a large tree into a repo
whose factory gates (manifest checksums, mirrored payload, doc scanners)
are built to treat every shipped file as owned.

**Licence.** MIT would not block redistribution inside the plugin, and the
copyright line keeps the Cocoon AI attribution. The open question is the
notices file for brand marks, not the code licence; any vendoring would need
to carry both.

**Supply chain and trust.** Installing a third-party skill into a plugin
means every user of the plugin runs another author's agent instructions and
executes its Node code with the user's permissions. Specific concerns, read
from its own text rather than observed behaviour: install goes through
`npx skills add`, which fetches and runs a package; `finalize` contacts a
project-hosted manifest on every delivery; the skill proposes editing the
user's global rules file; and the agent is told to launch a private browser
process. Mitigations the project documents are good (the update notice is
informational, summaries are treated as untrusted, nothing installs
itself), but a vended plugin cannot make those choices for its users. A user
who wants archify should install it themselves, scoped and pinned, with
eyes open. None of this was audited at code level here; the verdict is about
the shape, not a finding of bad behaviour.

## 4. Ideas that would genuinely help, ranked

| # | Idea | Class | Cost | Evidence |
|---|---|---|---|---|
| 1 | Claim discipline: state "automated checks passed; not visually reviewed" and never claim visual quality without looking at a render. Add to the four skills' final steps | borrow as text | a few lines each | archify `SKILL.md` Output and Delivery sections; our skills' "Done when" lines say nothing about what may be claimed |
| 2 | Fresh-IDs and "examples teach shape, not facts" rule: read one example, then author with new ids and wording, never copy the sample content. Our boilerplate rule ("replace the sample") is close; the explicit rule would harden it | borrow as text | one sentence per scaffold skill | archify authoring step 2 |
| 3 | A structural check on our own SVG outputs, stdlib Python: well-formed XML, one root `<svg>` with `viewBox`, finite numbers, no external `href`, every `marker-end` and `url(#id)` resolves, ids unique. Applied to the four boilerplates in `tests/` | needs tooling (small, stdlib, in-repo) | one test module, roughly 100 lines; no new dependency | archify's own gate list (single and finite SVG); the existing backlog item on the scaffold's missing `viewBox` shows a defect this would have caught |
| 4 | A model-first habit: write nodes, edges and boundaries as a small structured list (the "Model the system" step already does this in prose) and keep it next to the figure so a later edit starts from the model, not the pixels | borrow as text | a sentence naming where the model lives (for example a comment block in the SVG) | archify's JSON source is stored beside its HTML and each gallery item links its source |
| 5 | A receipt for diagrams that matter: after a check, record the source hash and the output hash so a later reader can tell whether the figure still matches what was verified | needs tooling | only worthwhile if idea 3 lands; otherwise noise | archify finalize receipt |
| 6 | Add ERD and lifecycle guidance. `mermaid` already routes `erDiagram` and `stateDiagram-v2`, so the gap is only for the static and animated SVG skills, which have no table-style entity or state-machine pattern | borrow as text, later, on demand | a design-system section per skill; do only if someone asks for a committed ERD figure | archify's table-first ERD rules (every physical column, key roles, one rectangle per domain) as a reference for what a good one needs |
| 7 | Adopt archify as code, or replace any of our four with it | reject | high: Node, browser, supply chain, a convention override | section 3 |
| 8 | The explainer-page feature and the rules-file write offer | reject | not a diagram problem, and it edits user config | `SKILL.md` Output section |

Ranked by value over cost: 1 and 2 first (free), then 3 (the only one that
moves quality mechanically and fits the conventions), then 4. Idea 5 waits on
3. Idea 6 waits on a request.

## 5. Recommendation

**Leave.** Not replace: the products differ (committed static SVG and
README-embedded motion versus a standalone HTML viewer), and the cost is a
convention break plus a trust change for every user of the plugin. Not a
wholesale update: most of what archify does well lives in code we should not
import. Take the free text-level lessons (ideas 1, 2, 4), consider one
stdlib SVG-structure check (idea 3), and tell users who want ten diagram
types and a browser-verified viewer that they can install archify
themselves; if we say so anywhere, it belongs in docs, not the plugin
payload.

Proposed follow-ups (not created):

1. `docs`/skills text: add a claim-discipline line and a fresh-ids rule to
   `architecture-diagram`, `animated-diagram` and
   `interactive-architecture-diagram`. Small, no tooling; touches `skills/`
   so it is its own PR and, per the release convention, gets a release PR
   afterwards.
2. `test`: a stdlib SVG-structure test over the diagram skills' boilerplates
   (idea 3), with the existing scaffold `viewBox` backlog item as its first
   case.
3. Optional, only on demand: an ERD or state-machine pattern for the static
   SVG skill (idea 6).

## What could not be verified

- No archify code was run; the quality of its output, the speed of the gates
  and the actual contents of a receipt are as the site and `SKILL.md`
  describe them, not observed.
- The JSON schemas were listed but not read, so "typed JSON IR" detail is
  limited to the file layout and the type router. The site itself does not
  document the schema; the repository does, in `schemas/`.
- Whether an exported SVG animates inside a GitHub README, the depth of the
  presentation mode, and the SVG export quality were not checked.
- Contributor counts are from the API's visible list and may not reflect the
  whole history; the "created 2026" reading rests on the licence year and
  release dates, not a creation timestamp.
- The supply-chain section is based on the shipped instructions and
  package manifests, not a code audit; the `skills` CLI that performs the
  install was not examined.
- The comparison to our skills is on text and structure; no side-by-side
  render of the same system was produced.
