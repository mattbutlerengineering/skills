# Issue #625, pass 2: what is actually working (evidence, not design)

Research note, 2026-10-10. This is a follow-up to `knowledge-base.md`.
The owner asked to "research solutions and what has been working first".

Each item below is tagged with an evidence strength:

- **[M-strong]**: a controlled, peer-reviewed or preregistered study with more than 100 tasks, or several studies that agree.
- **[M-weak]**: measured, but either small (under 60 tasks), single-vendor or not independently reproduced.
- **[A]**: anecdote, practitioner reports or star counts.
- **[V]**: a vendor marketing claim.

## 2. What's working: synthesis

Six findings recur across independent sources. Each is graded by strength.

1. **Context only pays when it carries information the agent cannot otherwise get.** Five sources point the same way:
   - Vercel: 53% to 100%, on APIs absent from training data.
   - Gloaguen: generated files help only once other docs are removed (+2.7 pts). Overviews did nothing.
   - DreamBench: memory helps when earlier evidence is non-inferable.
   - SWE-ContextBench: compact, correctly chosen experience gives +8 pts.
   - VibeMemBench: verified experience gives +1–4.5 pts.

   Everywhere the information was already inferable from the code, docs or training data, the effect was null or negative, and cost rose about 20%. **Strong, convergent.**

2. **Passive beats on-demand discovery.**
   - Skills went uninvoked 56% of the time (Vercel).
   - About 97% of llms.txt files are never fetched.
   - Memory systems that retrieve for themselves mostly fail (11 of 12 pairings in VibeMemBench). Self-selected experience *hurts* (−4 pts in SWE-ContextBench).

   What works is a **small, always-loaded index or pointer that the agent is told to use**, with the bodies read on demand. Strong for "discovery fails". Medium for "an index in the always-loaded file fixes it" (one vendor eval).

3. **LLM-generated, unverified knowledge is the measured loser.**
   - LLM-generated context files: −0.5 to −3 pts (Gloaguen).
   - DeepWiki's hallucinations reached users as bug reports.
   - Unfiltered memory retrieval hurts.
   - The Karpathy-wiki community's top failure mode is compounding errors, and its convergent fix is "agents draft, humans promote".

   **Strong.**

4. **Keep the always-loaded layer to guardrails and commands.**
   - Beneficial rules are negative constraints ("do not X").
   - Tool and command instructions are followed reliably.
   - Lean files speed runs up (−28.6% runtime).
   - Bloated files add reasoning tokens.
   - Correctness gains from content are small or not significant.

   **Medium–strong.**

5. **Structure maps and retrieval engines give small, real gains at a cost.**
   - RepoGraph: +2–2.7 pts.
   - Cursor A/B: +0.3% overall, +2.6% on large repos.
   - Graph MCP: an accuracy hit for a 10x token cut.

   The harness vendor that matters most here (Anthropic) abandoned vector RAG for agentic grep. Indexes **are not the bottleneck at project scale**. **Medium.**

6. **Maintenance is where knowledge bases die, and the fixes are mechanical.** Every popular file-memory pattern (Memory Bank, auto-memory, LLM Wiki, DeepWiki) has the same top complaint: staleness and drift. The fixes practitioners converged on:
   - source pointers and timestamps on claims, with the oldest re-verified first
   - supersession instead of silent rewrites; ACE measured that whole-document rewrites cause "context collapse", while itemised deltas avoid it
   - caps on index and page size
   - scheduled lint

   One known gap: lint catches internal contradictions, **not** notes that are wrong about the code. **Strong as consensus; unmeasured as an intervention.**

What has **no** evidence of working:

- Memory Bank (none measured)
- the LLM Wiki *for coding* (no eval at all)
- llms.txt as discovery
- DeepWiki
- third-party memory layers for coding (mem0, Letta)
- Serena's token claims

## 3. Verdict on the earlier recommendation (Option A)

**The evidence confirms A's skeleton and changes five details. It overturns nothing in the ranking.** B, C and D stay where they were, for the same reasons. D in particular is reinforced: retrieval engines show small lifts and Claude Code itself dropped vector RAG.

**Confirmed:**

- Cold pages read on demand, behind a small index: Vercel, Codified Context, and practitioner consensus.
- A content rubric that bans overviews (Gloaguen).
- Mechanical freshness from `sources:` plus `verified: <sha>` (the convergent practitioner fix).
- A flat index with no search engine at project scale (100–500 page rule of thumb, RepoGraph/Cursor deltas).
- Deferring C and rejecting D.

**Changed:**

1. **Put the index where the agent cannot miss it.** A's plan was a one-line pointer to `docs/kb/index.md`. Vercel shows that agents skip on-demand discovery about half the time. Revise this: `kb.py index` generates a **compressed, budgeted index block inside CLAUDE.md/AGENTS.md**, one line per page, under about 2KB, between managed markers, with page bodies still read on demand. If the owner rejects growing CLAUDE.md, the fallback is the pointer line plus an explicit "read before editing X" trigger. Either way, the eval in item 5 decides.
2. **Narrow the rubric from "knowledge" to "non-inferable knowledge".** Admit a page only if it states something the code, README, or a strong model's training data would not tell an agent. Examples: invariants, cross-module contracts, historical gotchas, external-system facts, and what was tried and failed, with citations to ADRs. Move **negative-constraint guardrails** to the always-loaded layer, not to KB pages, per Guardrails Beat Guidance.
3. **Drop Karpathy's auto-filing of query answers, and gate ingest.** LLM-written, unverified content is the measured loser, and compounding errors are the community's top failure mode. Ingest *proposes* a page diff, and a human, or the existing review/PR gate, promotes it. Nothing is self-filed from a query. Stamp every factual claim with a source pointer.
4. **Apply ACE/supersession-style updates, not rewrites.** Ingest uses itemised ADD/UPDATE/DELETE/NOOP deltas (already in A, and now evidence-backed). It marks superseded claims instead of silently overwriting them, and it never regenerates a page wholesale.
5. **Ship a with/without eval before graduating.** Every serious study's headline recommendation is "evaluate before deploying", and effects were repo- and agent-specific (40% of tasks changed difficulty band by agent; Khatri). The LEDGER row graduates only on a small paired ablation on this repo: the same N tasks with the KB block present and absent, measuring pass rate *and* tokens/steps. `charter_replay.py` already has the replay-and-score shape to borrow. The evidence predicts the most likely real win is **efficiency** (tokens, steps, runtime), not correctness. The eval should say so up front.

**Revised recommendation:** keep the one utility skill, `knowledge-base`, with setup, ingest and lint flows, plus a stdlib `kb.py` (`index` / `lint` / `stats`). Make these four changes:

- generate a compressed index block into the always-loaded file
- admit only non-inferable pages, with source pointers
- make ingest propose-and-promote with supersession, and drop query auto-filing
- gate graduation on a paired with/without ablation that measures tokens as well as pass rate

Keep C (`kb.py map`) parked until that ablation shows the KB itself pays. The best-measured structural lift is about +2 pts.

**First question for the owner (one at a time):** should the generated index live *inside* CLAUDE.md, about 2KB between markers, or behind a one-line pointer? Recommendation: inside. It is the single largest measured effect in this whole survey (Vercel 53% to 100%). The cost is a few hundred always-loaded tokens, which the dogfood ablation will price.
